# Аудит репозиторію «Де гроші?» (16.07.2026)

Повний аудит обох версій бота: локальної Python-версії (`bot.py`, aiogram 3 + SQLite)
і продакшн Cloudflare Worker (`src/index.js` + D1). Обидві кодові бази прочитані повністю.

---

## 1. Структура проєкту

**Python (локальний режим):** `bot.py` (5555 рядків) + модулі `analytics.py`, `monthly_report.py`,
`category_detector.py`, `category_details.py`, `compact_views.py`, `ai_insights.py`,
`ai_assistant.py`, `ai_cache.py`, `prompts.py`. БД — `expenses.db` (SQLite), конфіг — `.env`.

**Worker (продакшн):** `src/index.js` (~2190 рядків, вся логіка в одному файлі) +
`migrations/*.sql` (схема D1) + `wrangler.toml` (крони: щоденний 07:00 UTC, тижневий нд 17:00 UTC).
Конфіг — секрети Cloudflare / `.dev.vars`.

Це два незалежні переписування, не порт: дублюються парсинг сум/дат, категоризація,
статистика, типи «планова/емоційна», paywall/оплати — але зі своїми схемами БД і поведінкою.

`bot.py` компілюється (`py_compile` OK), усі модулі імпортуються (aiogram встановлений,
токен з `.env`, побічних ефектів на рівні модуля немає).

## 2. Баги: `src/index.js` (продакшн — пріоритет)

Рядки вказані для поточної версії файлу (після UX-правок).

### Критичні

1. **`src/index.js:161` — необроблені винятки у webhook → Telegram повторює update → дублікати витрат.**
   `request.json()` і `handleUpdate()` без try/catch: будь-який збій (битий JSON, помилка D1,
   збій fetch до Telegram) → 500 → Telegram шле той самий update знову. Мультивитрата
   «кава 80, таксі 150, хліб 20»: перші два INSERT пройшли, третій упав → повторна доставка →
   дублікати. Немає дедуплікації за `update_id`; «отруйний» update блокує чергу webhook.
   *Фікс:* try/catch + завжди 200; дедуп останніх `update_id`.

2. **`src/index.js:826` + `:472` — стан `pending_type` один на юзера: друга витрата затирає першу.**
   Кнопки «Планова/Емоційна» не несуть id витрати. Написав «кава 80», одразу «таксі 150»,
   тап «Планова» на першій картці → зберігається таксі, кава мовчки втрачена. Подвійний тап
   по обох кнопках (два конкурентні webhook) → подвійна вставка (немає атомарного захоплення стану).
   *Фікс:* pending-витрати в окремій таблиці, id у `callback_data`, атомарне видалення при вставці.

### Середні

3. **`src/index.js:224`, `:574`, `:1937`, `:1900–1923` — платіжний флоу плутає тарифи.**
   (а) «я оплатив» текстом і голий callback `paid` завжди створюють заявку 390 грн/30 днів,
   навіть якщо юзер обрав `buy_7`. (б) `ensurePendingPayment` дедуплікує по `(user, tariff_days)`:
   buy_7 + buy_30 → дві pending-заявки. (в) confirm/reject оновлює всі pending юзера без `id` —
   журнал оплат бреше. *Фікс:* тариф у callback всюди; confirm/reject по `payments.id`.

4. **`src/index.js:154` — webhook-секрет fail-open.** Без `WEBHOOK_SECRET` будь-який POST
   приймається; підробивши `from.id` адміна, атакер виконує `/grant`/`/block`.
   *Фікс:* без секрета → 403.

5. **`src/index.js:889` — кома-десяткова сума ламає мультивитрати.** «кава 149,50» ріжеться
   по комі на дві «витрати» → помилка, хоча `parseAmount` (:958) і `AMOUNT_PATTERN` (:933)
   кому підтримують. *Фікс:* перед спліт-логікою склеїти `(\d),(\d{1,2})(?!\d)` → `$1.$2`.

### Дрібні

6. **`src/index.js:1870`** — `hasActiveAccess` парсить київський `access_until` як UTC →
   доступ живе на 2–3 год довше, `expired` о ~03:00 замість опівночі.
7. **`src/index.js:921`** — «31 червня» → 1 липня, «29 лютого» → 1 березня (rollover без перевірки).
8. **`src/index.js:224`** — заблокований юзер через «я оплатив» (стоїть до `ensureAccess`)
   може нескінченно спамити всіх адмінів заявками.
9. **`src/index.js:1671`** — власний період не перетинає межу року: «28.12-03.01» → помилка,
   а підказка радить той самий формат.
10. **`src/index.js:1285`, `:1303`** — редагування/видалення обрізане: 10 останніх днів,
    30 витрат/день, без пагінації і без попередження — старі записи невиправні.
11. **`wrangler.toml:6`** — тижневий cron о 17:00 UTC (= 20:00/19:00 Києва, плаває через DST):
    недільно-вечірні витрати не потрапляють у жоден тижневий звіт, хоча label каже Пн–Нд.
12. **`migrations/0001_initial.sql:19`** — `expenses.amount INTEGER`, а бот пише дробові
    (працює через type affinity, але схема бреше).

По бюджету багів немає: `budgetWarning`/`getMonthSpent` коректно рахують лише поточний місяць.

## 3. Баги: `bot.py` + модулі

### Критичні

1. **`category_detector.py:404` + `bot.py:1989` — синхронний OpenAI-виклик блокує весь бот.**
   `normalize_financial_category()` при незнайомій назві викликає `detect_category_gpt()` —
   синхронний HTTP до OpenAI (таймаут 8с) прямо в async-хендлерах: `save_expense`,
   `update_expense`, `get_top_categories_by_conditions` (на кожен рядок статистики!),
   `build_category_details`. Event loop стоїть — бот не відповідає нікому.
   *Фікс:* на sync-шляху тільки локальний детектор; GPT — окремим кроком через `asyncio.to_thread`.

2. **`bot.py:1936` — десяткова сума мовчки псує дані.** `parse_smart_expense_input` бере
   останнє `\d+`: «кава 149.50» → сума 50, назва «кава 149.»; «кава 1.5к» → сума 5.
   `parse_amount` (:1915) теж приймає лише цілі. *Фікс:* `\d+(?:[.,]\d+)?` + «к»-суфікс, як у Worker.

3. **`bot.py:756` — на кожному старті переписується вся таблиця expenses.** SELECT усіх рядків +
   UPDATE кожного через `normalize_financial_category` (може смикати GPT — див. №1).
   *Фікс:* разова міграція з маркером (`PRAGMA user_version`).

### Середні

4. **`bot.py:918`** — `has_access` без захисту `fromisoformat`; legacy unix-timestamp у
   `access_until` (їх підтримує `:1068`) → ValueError → юзер без відповіді.
5. **`bot.py:5158`** — мертва кнопка «✅ я оплатив» після `pay_info`: `paid_keyboard(0)` дає
   callback `paid_0`, якого немає ні у фільтрі хендлера (:5164), ні у whitelist middleware (:1891).
   «я оплатив» текстом створює pending з tariff=0/amount=0 (:5199).
6. **`bot.py:998`** — approve/reject оновлюють усі pending юзера без id (як у Worker).
7. **`bot.py:5550`** — `asyncio.create_task(scheduler(bot))` без збереження реф + без try/except
   у `while True`: перший виняток у `check_users` (напр., `strptime` на битому `last_activity`,
   :2988) назавжди вбиває всі авторозсилки.
8. **`bot.py:2440`** — статистика власного періоду рахується максимум по 1000 останніх записів
   (`CUSTOM_PERIOD_RECORD_LIMIT` застосовано і до SUM) — тихо занижені підсумки.
9. **`bot.py:2085`** — «Тиждень» обрізається межами місяця (1-го числа «тиждень» = 1 день).
10. **`compact_views.py:113`** — «Разом» у списку рахує лише показані 10 записів поруч із
    «... ще N витрат».

### Дрібні

- `bot.py:1250` і `:2942` — мертві дублікати блоків нагадувань (другий if недосяжний).
- `bot.py:5138` — `expense_type` із callback без валідації проти `{планова, емоційна}`.
- `bot.py:2239` — «Рік» = останні 365 днів (у Worker — календарний рік).
- `bot.py:3218` — «попередній місяць» = вікно [-60дн, -30дн], не календарний.
- `bot.py:2714` — одноденний власний період порівнюється сам із собою → завжди «стабільні».
- `bot.py:5232`, `:5253` — `bot.send_message` у confirm/reject без try: юзер заблокував бота →
  адмін не бачить підтвердження (доступ уже видано).
- `bot.py:1362` — «залишилось: 5 дні» (для ≥5 треба «днів»).
- **Мертвий код:** `ask_ai_assistant` (ai_assistant.py), `analytics.py`, `prompts.py`,
  `build_month_ai_summary`; у bot.py — `build_insights` (:2540), `stats_period_keyboard` /
  `list_period_keyboard` (:3526/:3540) і тому callback-хендлери `stats:`/`list:` (:5270/:5303)
  недосяжні з UI. AI-чат-асистент написаний, але не підключений.

**SQL-ін'єкцій немає в жодній версії** — всі запити параметризовані.

**Розбіжність типів:** Python пише `'планова'`/`'емоційна'` (поле `type`, буває NULL),
Worker — `'planned'`/`'emotional'` (поле `expense_type`, NOT NULL). Схеми БД несумісні
без конвертації.

## 7. Топ-5 рекомендацій

1. **P0 — Надійність webhook** (`src/index.js:161`): try/catch + завжди 200 + дедуп
   `update_id` + fail-closed `WEBHOOK_SECRET`. Прибирає дублікати витрат і закриває підробку
   адмін-команд.
2. **P0 — Полагодити `pending_type`** (`src/index.js:826`): id витрати в `callback_data`
   замість одного слота стану. Зараз ядровий флоу губить дані.
3. **P1 — Платіжний контур Worker** (`:224`, `:1900`): тариф у callback всюди, confirm/reject
   по `payments.id`, блокованим — без спаму адмінам.
4. **P1 — Парсинг сум**: Worker — кома-десяткова в мультивитратах (`:889`);
   Python — переписати `parse_smart_expense_input` або заморозити версію як legacy.
5. **P2 — Одна кодова база**: Worker = єдиний продакшн; перенести з Python список витрат,
   місячний GPT-звіт і рекомендації; уніфікувати літерали типів і задокументувати
   конвертацію SQLite → D1.
